NON-NEGOTIABLE ENGINEERING RULES
1. Hybrid architecture — sensitive data stays in MongoDB; only proofs go on-chain.
2. NEVER store donor names, phone numbers, emails, addresses, disease names, medical reports, passwords, or private keys on-chain. EVER.
3. Generate deterministic hashes from a fixed field order. For donor: `chainId|donorId|bloodGroup|lastDonationDate`. For blood unit: `chainId|unitId|donorId|bloodGroup|collectionDate|expiryDate|testStatus|availabilityStatus`. Use `ethers.keccak256(ethers.toUtf8Bytes(input))`. Never change the field order mid-project.
4. Compute verification hash identically on read and on write.
5. Use environment variables for every secret (.env). Never hardcode.
6. One source of truth — MongoDB for state, blockchain for proof. Do not copy state from chain back into DB on reads.
7. Strict mode in every JS file.
8. Consistent error envelope: { error: string, code: string }. Use 400 validation, 401 unauthenticated, 403 unauthorized, 404 missing, 409 state conflict, 500 unexpected.
9. CORS allows http://localhost:5173 only.
10. Output one milestone at a time. After each module: list changed files, new routes, and the exact curl or browser steps to manually verify.

MODULE 1 — Authentication and Roles
DO: User model {name,email unique,passwordHash,role enum donor|admin|hospital,createdAt}. bcryptjs cost 10. JWT 24h. Routes: POST /api/auth/register (always donor), POST /api/auth/login returns token + role, GET /api/auth/me. Middleware auth.js injects req.user. Middleware role.js accepts allowed roles array, returns 403 on mismatch. Frontend AuthContext stores user+token in localStorage, Axios interceptor injects Authorization header.
DO NOT: return passwordHash. Do not let self-registration pick role=admin or role=hospital.
ACCEPT: register donor → login → /me works. Token persists across refresh.

MODULE 2 — Donor Registration and Admin Verification
DO: Donor model {userId ref User, donorId unique DNR001…, name, age, gender, bloodGroup, phone, email, address, city, pincode, lastDonationDate nullable, eligibilityStatus enum pending|verified|flagged, isVerified, isFlagged, flagReason, donationCount, createdAt, blockchainTxHash}. POST /api/donors/register (donor). GET /api/donors/pending (admin). GET /api/donors (admin, filters bloodGroup,pincode,isVerified,isFlagged). PUT /api/donors/:donorId/verify (admin) calls verifyDonor(donorId, donorHash) on contract, stores tx hash. PUT /api/donors/:donorId/flag body {flag:bool, reason} calls flagDonor with reason's keccak256 — reason text stays in MongoDB only.
DO NOT: write flagReason text on-chain. Do not let donors edit isVerified/isFlagged.
ACCEPT: pending donor gets verified; profile shows verified and non-empty blockchainTxHash.

MODULE 3 — Smart Donation Interval Checker
DO: 90-day minimum gap. eligible iff today - lastDonationDate >= 90 days OR lastDonationDate is null. POST /api/donors/check-eligibility body {donorId} returns {eligible, nextEligibleDate, daysSinceLastDonation, ruleDays:90}.
DO NOT: read from chain for eligibility. Blood unit creation must call the same checker.
ACCEPT: a donor with lastDonationDate 30 days ago cannot be assigned a new unit; API returns 409.

MODULE 4 — Blood Unit Management
DO: BloodUnit model {unitId unique BU001…, donorId ref Donor, bloodGroup, collectionDate, expiryDate, testStatus enum pending|safe|rejected, availabilityStatus enum collected|testing|available|requested|issued|expired|rejected, storageLocation, qrUrl, blockchainTxHash, createdAt, updatedAt}. POST /api/blood-units validates donor verified+eligible+notflagged; expiryDate = collectionDate + 35 days; status collected + testStatus pending; generate unitId; generate QR pointing to frontend /verify/<unitId>; call addBloodUnit(unitId, unitHash, 'collected'); return unit with QR dataURL. PUT /api/blood-units/:unitId/test-status {status:'safe'|'rejected'} — safe → availability available; rejected → both rejected; emits updateBloodUnitStatus. PUT /api/blood-units/:unitId/availability (admin) enforcing the state machine. GET /api/blood-units supports filters. Cron or GET /api/blood-units/refresh-expiry marks past-expiry units as expired and writes trace + on-chain update.
ALLOWED STATE MACHINE: collected → testing → available → requested → issued → expired. Any state → rejected (terminal).
DO NOT: skip the state machine. Reverse testStatus=rejected. Issue expired or rejected units.
ACCEPT: every state change writes a trace and a tx hash; creating for an ineligible or flagged donor returns 409.

MODULE 5 — QR Code Generation and Verification Page
DO: qrcode package generates dataURL for /verify/<unitId>. /verify/:unitId is a public route (no auth). Displays unitId, bloodGroup, collectionDate, expiryDate, testStatus, availabilityStatus. Shows "Blockchain Verified" green or "Record mismatch — possible tampering" red plus last verified timestamp. Backend GET /api/verify/:unitId returns { dbHash, chainHash, match, chainStatus, dbStatus }.
DO NOT: put verification logic on-chain. Do not display donor name, phone, address, or medical details.
ACCEPT: manually editing one selected DB field flips match=false on next QR scan; revert flips back true.
